## 1. 为什么必须串行

本机是一台 8 GB 显存的 Intel Arc A750：Qwen3-30B-A3B（Q4_K_M，SYCL）
实测独占约 2.7 GB 显存，QSV 编码器初始化还要预留编码引擎与帧缓冲。
过去“先手动开 llama-server、再开 CosyVoice”的用法留下过两个真实故障：

1. 两个模型进程常驻时，`h264_qsv` 会在初始化阶段失败或悄悄回退到软件编码；
2. 手动启动的服务不会被回收。实测在 8080 与 50000 之外还残留了一个
   不监听端口的 CosyVoice 进程（`api_server.py`），持续占用内存与句柄。

因此流水线不再假设“服务已经在跑”，而是**由流水线自己按阶段启停**：
任何时刻只有一个重量级进程，用完立刻杀掉，等驱动释放显存后再进入下一阶段。

## 2. 五条硬规则

| # | 规则 | 实现位置 |
|---|---|---|
| 1 | 同一时刻只允许一个重量级进程（llama-server / CosyVoice / FFmpeg-QSV） | `assert_quiet()`、`quiet_stage`、`PipelineLock` |
| 2 | 启动后轮询 `/health`，就绪立即执行，禁止固定 `sleep` | `ManagedService._wait_ready()`（1 s / 0.5 s 轮询） |
| 3 | 结束必须 `taskkill /F /T /PID` 清理整棵进程树，验证进程与端口都消失 | `kill_tree()`、`stop()` |
| 4 | 杀掉模型后强制冷却 **2 秒**，等 Intel 驱动释放显存 | `COOLDOWN_S = 2.0` |
| 5 | 清理必须在 `finally` / `__exit__` 中执行，异常、Ctrl-C、健康检查失败都不例外 | `ManagedService.__exit__` |

判定“重量级进程”只看进程本身，不看命令行文本：`bash.exe -c "... llama-server ..."`
这种只是提到名字的 shell 不算，避免把工具链误杀。

## 3. 四阶段互斥流水线

| 阶段 | 独占资源 | 工作内容 | 结束动作 |
|---|---|---|---|
| 1 文本理解与高光规划 | `llama-server`（8080，SYCL） | 高光候选提取（Cue ID，可选）+ 5W1H 片头文案（JSON） | `taskkill /F /T` → 端口释放 → 冷却 2 s |
| 2 语音合成与时间审计 | CosyVoice2（50000，CPU） | `intro_voice.wav`；6.0–9.5 s 审计，超标仅用 `atempo ≤ 1.15` 微调 | 同上 |
| 3 视觉卡片生成 | 无（Chrome headless） | 固定工业模板 → 两张确定性 PNG（state 0 / 1） | 浏览器进程自行退出；校验无模型存活 |
| 4 媒体渲染与成片装配 | FFmpeg / QSV | 片头 6–9.5 s（60 fps）→ 规格归一化 → concat demuxer `-c copy` 拼合集（必要时有界重编码）；ffprobe + join 解码验收 | 结束后再次审计，残留模型进程会被清掉 |

阶段 4 开始前 `quiet_stage` 会再检查一次：只要还有任何模型进程存活就拒绝开编，
避免“模型加载期间启动 QSV”导致的抢占失败。合集默认走 concat demuxer 流拷贝
（不把多路 1080p60 塞进一个 `filter_complex`），资源占用见
[`自动剪辑-高光切片方案.md`](自动剪辑-高光切片方案.md) 第 15 节。

### 阶段 2 超时怎么办

按规范，阶段 2 只允许 `atempo`（上限 1.15×）。如果加速后仍放不进 9.5 s：

1. CosyVoice 进程树被杀（`with` 块抛异常，`__exit__` 清理）；
2. 冷却 2 s 后重新打开 **llama-server** 窗口，让 Qwen 压缩口播（`stage_rewrite`）；
3. 杀掉 LLM、冷却 2 s，再开 CosyVoice 重新合成；
4. 最多 `--max-voice-repairs 2` 次；仍失败则整条流水线失败并保留现场。

这条修复路径同样遵守“一次只有一个重量级进程”，测试
`test_tts_overshoot_reopens_llm_only_after_tts_exit` 会断言先后顺序。

## 4. 控制器 API

```python
import resource_manager as rm

with rm.PipelineLock():                 # 一台机器只允许一条流水线
    with rm.llama_server() as llm:      # 启动 → 轮询 /health → 就绪
        ...                             # 此时系统内没有其它重量级进程
    # 树已杀、端口已释放、冷却 2 s 完成
    with rm.cosyvoice() as tts:
        ...
    with rm.quiet_stage("qsv encode"):  # 断言无模型进程
        ...
```

关键行为：

- **复用而不是重复启动**：目标端口已有同类服务时 `ManagedService` 接管该进程
  （`adopted`），阶段结束时照样杀掉，落实“用完即杀”。
- **端口被无关进程占用**：直接抛 `ResourceBusyError`，不会误杀。
- **启动器进程**：Windows 上 `venv\Scripts\python.exe` 往往只是启动器，
  真正监听的是它的子进程。`stop()` 在杀掉进程树之后还会检查端口属主，
  把逃逸到树外的监听进程一并清理。
- **显存记录**：停止 llama-server 前用 Windows GPU 性能计数器读该进程的
  Dedicated Usage，写进日志（`vram 2696 MiB`），便于确认释放。

可配置环境变量：

| 变量 | 默认值 | 说明 |
|---|---|---|
| `LLAMA_SERVER_BIN` | `D:\AI\bin-sycl\llama-server.exe` | llama.cpp SYCL 构建 |
| `LLAMA_MODEL_PATH` | `D:\AI\models\Qwen3-30B-A3B-Instruct-2507-Q4_K_M.gguf` | 主模型 |
| `LLAMA_PORT` / `COSY_PORT` | `8080` / `50000` | 监听端口 |
| `COSYVOICE_DIR` | `D:\AI\CosyVoice-Runtime` | CosyVoice 独立运行时 |

## 5. 命令

```powershell
# 一条命令跑完四阶段（推荐）
uv run python scripts/run_pipeline.py --video-id c88l8daXiv4 `
  --srt "subtitles/c88l8daXiv4.zh.bilingual.srt" `
  --title "..." --summary "..." --series "AI 基建 / 第 21 期" `
  --speaker "DYLAN PATEL / SEMIANALYSIS" --source "SemiAnalysis × Daytona" `
  --stamp "FIELD RECORD / 2026" --stamp-right "2026 / DATACENTER · CPU" `
  --index 021 --reuse-analysis

# 只做资源侧运维
uv run python scripts/run_pipeline.py --status     # 列出模型进程、端口、显存
uv run python scripts/run_pipeline.py --cleanup    # 杀掉所有模型 / ffmpeg 进程树

# 单独重跑某一阶段（默认假设服务已在运行；--manage-services 由脚本自己启停）
uv run python scripts/generate_intro.py --video-id c88l8daXiv4 --stage copy --manage-services ...
uv run python scripts/generate_intro.py --video-id c88l8daXiv4 --stage voice --manage-services
uv run python scripts/generate_intro.py --video-id c88l8daXiv4 --stage picture
uv run python scripts/generate_intro.py --video-id c88l8daXiv4 --stage render
```

`generate_intro.py --stage all` 会转到同一条串行流水线，不再自行猜测服务状态。

新增参数：

| 参数 | 作用 |
|---|---|
| `--reanalyze` | 忽略已有 `analysis.json`，在阶段 1 重新调用 LLM 提候选 |
| `--render-clips` | 阶段 4 先用 `auto_clip --reuse-analysis` 渲染切片，再拼合集 |
| `--skip-assembly` | 只产出片头，不拼最终合集 |
| `--max-voice-repairs N` | 口播超窗时允许的 LLM 压缩次数（默认 2） |

## 6. 异常与兜底

| 情况 | 行为 |
|---|---|
| 健康检查超时 | 杀掉刚启动的进程树，异常信息附带服务日志末尾 12 行 |
| 服务进程提前退出 | 立即失败，不白等超时 |
| 端口被无关进程占用 | `ResourceBusyError`，不做任何 kill |
| 阶段内异常 / Ctrl-C | `__exit__` 强制执行 `taskkill`、验证端口、冷却 |
| 阶段 4 前发现模型残留 | 拒绝开编并提示 `run_pipeline.py --cleanup` |
| 流水线结束仍有残留 | 最终审计记录 `resource_audit` 并杀掉残留模型进程 |
| 锁文件残留 | 持有者 pid 已消失时自动判定为过期并接管；进程仍在则拒绝 |
| 端口未在 10 s 内释放 | 抛 `ResourceBusyError`，报告中带上端口属主 pid |

## 7. 日志与产物

每个阶段都会打印四类状态，便于人工核对：

```
[HH:MM:SS] [resource] llama-server: 已启动 (spawning, port 8080)
[HH:MM:SS] [resource] llama-server: 已完成 health check (...)
[HH:MM:SS] [resource] stage 1/4 LLM 已完成 (12.3s)
[HH:MM:SS] [resource] llama-server: 清理 (reason: stage finished, pid 3456, vram 2696 MiB)
[HH:MM:SS] [resource] llama-server: 冷却中 2.0s
[HH:MM:SS] [resource] llama-server: 已清理 (pid 3456 gone, port 8080 free)
```

产物：

| 路径 | 内容 |
|---|---|
| `clips/<id>/pipeline.json` | 四阶段状态、耗时、服务、错误、`resource_audit` |
| `clips/<id>/intro/pipeline.json` | `generate_intro.py --stage all` 单独运行时的阶段记录 |
| `clips/<id>/intro/{copy,narration,picture}.json` | 阶段间交接文件（可单阶段重跑） |
| `.runtime/logs/llama-server.log` | llama-server stdout/stderr |
| `.runtime/logs/cosyvoice.log` | CosyVoice stdout/stderr |
| `.runtime/pipeline.lock` | 单实例锁（正常结束时删除） |
